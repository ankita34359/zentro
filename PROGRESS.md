**Decisions made without asking (recommended answers)**
- **People without a login are "directory people"** (a membership with no user, status `active`). Inviting someone still creates their own person; linking an existing directory person to an invitation is not built (known limitation).

Nobody verifies their own evidence; rejecting or asking for more needs a reason; everything is audited. Evidence shows in the task drawer and the objective drawer, and beside each record on a scorecard ("2 evidence (1 verified)"): **it does not change a score or its confidence** (no model expects evidence yet), and a viewer counts only the evidence they may see.

A test walks Scenario 3 end to end: the employee updates a task and attaches evidence, the manager sees both and verifies, and after the employee records the outcome on the key result its value moves.
- **Decisions:** (1) a viewer sees evidence if they submitted it, if it is about them and not restricted, if it is organization-level and they hold `evidence.view`, if it is scope-level and their `evidence.view` reaches the person it is about, or if it is restricted and their `evidence.view_restricted` reaches that person; (2) files travel as base64 in a JSON body with a 3.5 MB limit on `/api/evidence` only (no new dependency); (3) one file per piece of evidence.

## Key findings that shaped the plan

1. **Embarko's docs state no Node version.** `engines.node: ">=20"` produced Node 20.20.2 in HireDrive/Curevia. Pin to that.
2. **`better-sqlite3@13` and `vitest@5` need Node 22+.** Use `better-sqlite3 ^12.11` and `vitest ^4.1.12` (changed from 3.2 in stage 1.1). Vite 8 needs `^20.19`.
3. **Curevia and HireDrive are plain JavaScript.** A compiled TypeScript backend is unproven on Embarko (stage 1.1 proves it; fallbacks `tsx`, then plain JS).
4. **Curevia uses DB sessions and bcryptjs, not JWT and scrypt.** The override asks for JWT + scrypt; the plan keeps JWT but backs it with a revocable session row.
5. **Embarko file storage is public by link.** Not usable for confidential evidence; evidence files go in capped SQLite BLOBs behind an authenticated route.
6. **viaSocket's AI assistant has web search and a browser always on**, and its tools are public HTTP endpoints. The orchestrator therefore runs the tool loop in-process (decision D10).
7. **`viasocket-apps` is at 0.21.0**; Curevia pins `^0.7.0` (API changed). Re-verify at stage 8.
8. Scheduler: max 5 schedules, ≥5 min apart, 5 min per call, GET with `Bearer CRON_SECRET`, missed runs not replayed. One 5-minute tick with a job registry.

## Stage 1.2: backend foundation (complete, live)

**Implemented** (branch `claude/stage-1-2`, commit message starts "Stage 1.2"; design notes in `docs/architecture.md` section 8.1):
- **Config validation + holding page.** Required: `SESSION_SECRET`, `ENCRYPTION_KEY` (each at least 32 characters, different). Optional and validated if set: `APP_URL`, `LOG_LEVEL`, `TRUST_PROXY`. If anything is missing or invalid the server **still listens** in holding mode: the site address shows a plain notice, every `/api/*` answers `503 server_missing_settings` with `Server is missing: SESSION_SECRET` (names only; a bad value is never echoed), `/healthz` answers `ok:true, ready:false`, the cron route authenticates and does nothing, and **the database is not opened**.

Malformed JSON → 400 `invalid_json`; body over 100 KB → 413.
- **Route registry with permission markers.** `public` (needs a written reason) / `cron` / `baseline` / `permission(key)`, Zod validation, boot-time check that nothing bypasses the registry. Until sessions exist (2.1) `baseline` and `permission` routes fail closed (401).

### Restore backup at start-up (2026-11-23, owner asked; built on `claude/stage-2-3`)
- **What:** the environment variable `RESTORE_BACKUP=<backup file name>` (`backend/src/db/restore.ts`, called from `server.ts` before the database is opened). Plain file names from `<data>/backups/` only; the file must be a real SQLite file passing `PRAGMA integrity_check` with a `schema_migrations` table. It **takes a fresh backup of the current data first** (`pre-restore-<time>.db`, or the raw files if the current database is unreadable; the newest three kept), replaces the database, and logs `restore requested`, `fresh backup of the current data taken before restoring`, `restore completed` (no data in the lines). **Runs once per value**: the request is recorded in `<data>/restore-log.json`; the same value on the next restart logs `restore already applied` and changes nothing; a different value (append `@label`) runs again. A refusal (bad name, missing, not SQLite, damaged, not Zentro's) changes nothing and logs an error. Never set on the live app unless the owner asks; nothing is set now.
- **Tests:** `tests/restore.test.ts` (9): nothing requested does nothing; restore after a fresh full backup and the exact log lines; **runs once** (later data survives a restart, no extra safety backup, record unchanged after several restarts); a new value runs again and backs up the work done in between; refuses path tricks and bad names; refuses missing, non-SQLite, non-Zentro and truncated files before changing anything; unreadable current database kept as raw files; migrations apply on top of a restored older database; only the newest three safety backups kept.
